# QueueExecutor failover with durable capacity ownership

Status: proposed implementation-ready design for [#2199](https://github.com/jlapenna/agent-lcars/issues/2199). This document selects an application architecture; the running controller remains a singleton. Implementation and the separately approved Homelab qualification must land before R8 can be called shipped.

## Decision and invariant

Use server-owned, transactional capacity receipts shared by all executors in one explicitly configured pool. Executors may claim concurrently; there is no exclusive launch leader whose lease expiry would be mistaken for fencing. Keep local node/readiness checks as an admission prerequisite, but replace their process-local reservation as the authority for the fleet limit.

For pool limit `N`, at every durable transition:

`occupied capacity receipts <= N`

Each potentially executable attempt owns exactly one occupied receipt. `max_concurrent` remains an attempt/unfinished-Job admission limit, not a literal count of Kubernetes Pods; duplicate bootstrap Pods are possible. A receipt covers claim-to-Job gaps, suspended Jobs, unplaced Pods, running and terminating workers, and uncertain former producers. Releasing an execution lease, finishing a run, changing controller identity, or observing an absent Job does **not** release capacity. Provider ceilings use the same potentially executable receipts, including receipts whose run was settled lost. Queued retries remain queued until their predecessor is physically retired.

This preserves conservative attempt occupancy beyond the logical run lease. Kubernetes cannot promise exactly-once processes in all node failures. Current run tokens and provider leases do not distinguish duplicate Pods for one attempt; the new mode therefore also requires the worker-generation activation gate below before any provider invocation. Unknown physical worker state is occupied capacity. Under partition the pool can lose usable slots; it must not invent safe capacity to meet an availability target.

## Durable model and API

The existing orchestrator database owns the new records; executors continue to use the Work API and never receive Firestore access. Add owning schemas, memory/Firestore implementations, generated contracts, and authoritative metrics together.

- Pool policy: immutable `poolId`, Kubernetes cluster identity and namespace, validated `maxConcurrent`, one-unplaced limit (initially 1), and monotonically increasing policy version. The server maps an executor grant to its pool; request fields cannot select another pool or raise its limit. Reject mismatched cluster/namespace/config versions before a claim. Changing `N` downward drains occupancy before accepting new claims.
- Fixed slots: `poolId`, `slotId` in `0..N-1`, revision, state, optional exact `runId`, claimant subject/runner, random receipt nonce, producer incarnation, created/updated timestamps, and optional verified Job UID. Retain retired-run identities separately from recyclable slot state. No run token is stored here or printed in evidence.
- Receipt states: `free -> claimed-unplaced -> placed -> retiring -> free`; `quarantined` is an occupied state reachable from any uncertainty. Recovery ownership has a distinct bounded lease and nonce; expiry changes who may investigate, never occupancy.
- Provider capacity domains: the server maps each pipeline/credential/backend to a capacity domain shared across **all** configured pools. The Codex/OpenCode ceiling stays global for a shared subscription/backend. Claim transactions read and CAS the shared domain occupancy together with the pool slot and run. Occupancy is the deduplicated union of occupied receipts and legacy live claims during migration; a lost/finished run with an uncertain worker still occupies its domain. A per-pool-only query or a client-selected domain is forbidden. Unknown migration inventory blocks every affected domain.
- Claims: extend the existing transaction to require pool policy, a free slot, the pool-wide unplaced allowance, provider ceiling, grant and cooldown. Run claim, receipt allocation and the unplaced allowance commit together. No free slot returns the existing bounded capacity-wait semantics without a run claim. A stale/unrecognized pool version is an actionable refusal, not an empty queue.
- Claim-response loss: require a caller-generated `claimRequestId` scoped to the authenticated pool/subject/producer incarnation and durably bind it to the exact run/slot/token hash in the claim transaction. The replay response is a discriminated union: `claim` for the first returned secret, `recover-owned-secret` with exact run/Job identity and no new token, or `quarantined-unrecoverable-token`. Never promise token recovery from a hash. An identical retry cannot claim a second run; a different request ID cannot bypass an unresolved producer claim. Incarnation registration is durable and closed on quiescence/fencing; an old incarnation cannot register or replay as a new producer. A successor obtains a receipt-bound recovery lease under current grants and uses the immutable owned Secret if available. A missing Secret with an unrecoverable token stays quarantined until the retirement barrier below is complete.
- Bind/place: a server procedure accepts the exact run/receipt nonce and Job UID after the executor reads the deterministic name, run annotation and ownership. `placed` requires a nonterminal owned Pod with a node assignment. Replacement UID, deleting Job, foreign owner, inconsistent placement, or failed API reads remain occupied/unknown. Only a confirmed placement releases the pool-wide unplaced allowance.
- Worker completion continues through the existing run-token route. It settles logical work but does not free a physical slot. Exit reports keep the original subject/runner check; successor recovery is a new explicitly authorized protocol and does not impersonate a changed principal.

Store methods must acquire receipts and run/provider reads in one transaction. A query followed by a separate increment is not sufficient. Every release compares slot revision, run ID, receipt nonce and exact Job UID; an old generation cannot free a newer attempt's slot. The memory implementation must enforce the same races as Firestore rather than relying on caller serialization.

## Split brain, restart, and retirement

Every controller incarnation registers a unique producer identity. Launch RPCs belong to a receipt-scoped operation group. Graceful retirement stops new RPCs, waits for every operation to receive a definitive response, and acknowledges quiescence; timed-out/ambiguous writes are **not** acknowledged as drained. A restarted process cannot revive its old operation group. This producer protocol is part of the implementation, not an inference from a heartbeat.

A successor can inventory and recover an original never-started suspended Job under the existing UID/generation/Secret/live-token fences. It does not need to steal or recycle the occupied slot. An older producer launching the same still-valid attempt still consumes that same receipt and deterministic Job. Different attempts require different occupied slots. Recovery/retirement are serialized per receipt and UID; a stale delete is never allowed to race a new resume.

Before provider invocation, each trusted direct-runner bootstrap presents its immutable Kubernetes Pod UID, Job UID and run-token identity to a new receipt-bound activation procedure. An executor inventory attests the exact owned Pod; arbitrary client-supplied UIDs cannot acquire a permit. One transaction records one active worker generation for the receipt and provider domain. Concurrent duplicate Pods are denied before invoking Claude, Codex or OpenCode. Activation/heartbeat/completion contracts bind to that generation; the original shared run token alone is insufficient. Mounted provider keys do not authorize bypassing this trusted bootstrap gate. A successor worker generation needs positive retirement of the previous worker, never merely heartbeat/lease expiry. Unknown/unreachable workers retain the permit and quarantine. This is an implementation prerequisite for claiming a provider-execution bound; it cannot impose a literal Pod-count bound on Kubernetes bootstrap duplication.

Physical retirement requires all of:

1. Transactionally enter `retiring` for the exact receipt/worker generation. Reject future activation, recovery and token use for that attempt, while retaining its occupied slot/domain. Preserve a permanent retired-run record distinct from the recyclable slot. No lease or completion alone crosses this barrier.
2. All producers authorized for the attempt are positively quiescent or fenced against **new** RPCs. A lease/heartbeat timeout, SIGUSR1 toggle, canceled client request, or deletion request is not proof. Homelab must positively terminate and prevent restart of an unreachable exact runtime incarnation; the application validates the receipt-bound acknowledgement through a separately scoped configured fencing authority. Ordinary executors cannot attest another producer died. This does not drain previously accepted server-side RPCs: the following Kubernetes barrier is also mandatory.
3. Install and observe a deterministic-name **inert Job tombstone** after producer fencing. If the name is absent, atomically create an original suspended Job without a usable run credential, marked with the exact retired run/receipt nonce. A delayed original Create racing this write either wins (inspect and retire that exact UID) or loses with AlreadyExists. If the Job exists, require either confirmed terminal state with all owned Pods terminated, or the original generation-1 suspended, never-attempted specification with no owned Pods; atomically CAS its UID/resourceVersion into the inert retirement state. This permits safe retirement of missing-Secret shells. A previously executing or deleting Job is not a never-started shell: wait for all physical workers to terminate and deletion to finish, then install a fresh-UID tombstone before release. Unknown lists or unreachable workers remain occupied. Never force-delete to infer termination.
4. Read back the barrier UID/resourceVersion and attest it to the retiring receipt. Previously queued unsuspend/delete writes must carry their original UID/resourceVersion and fail against the updated/replaced tombstone. New mode forbids unconditional producer updates/deletes. Old client-side retries cannot resume because producers were quiesced/fenced and server retirement rejects recovery. Only after that durable barrier and physical evidence may a transaction release the slot/domain and any unplaced allowance. Recognized server-retired inert tombstones do not count as executable attempts; an arbitrary label cannot exempt a Job. Keep the tombstone while **any ambiguous RPC lacks a definitive outcome**, even if the producer is dead; remove it only after the receipt-bound operation ledger proves all authorized writes resolved. Unknown writes mean retained inert storage, not permission to remove the name barrier.

New mode removes automatic Job TTL until receipt-aware cleanup is proven: a TTL must not erase the only tombstone while a producer is unresolved. A bounded sweep retries quarantine inspection; it never deletes on age alone. Uncertain workers or failure to install the barrier keep capacity occupied. After a proven inert barrier, unresolved RPCs retain the tombstone indefinitely as explicit storage debt with an alert; they cannot create an executable attempt or permit early tombstone deletion.

For a lost logical run with a surviving worker, keep its receipt/provider occupancy while admitting at most a queued retry through normal orchestration. Do not claim that retry until physical retirement. For missing pre-Job state, positive producer fencing plus a freshly observed inert name barrier may retire it; a timeout alone cannot. Duplicate completion, delayed recovery/bind/retire messages and policy changes cannot free or overwrite another run's receipt.

## Schedule, maintenance, and convergence authority

There is no shared launch leader. Every healthy replica may call the separately granted `work.cron` endpoints at startup and every five minutes; the server's deterministic schedule-slot admission, orchestrator transactions and outbox claim leases remain the authority. Verify concurrent maintenance as well as schedule ticks before enabling replicas. One replica's Kubernetes/preflight failure must not stop its otherwise authorized cron clock.

Add jitter bounded within the existing five-minute cadence and single-flight calls per replica. Outbox settlement retains its exact claim ID fence. Physical receipt reconciliation uses its own per-receipt lease and does not sit on the claim request path. All replicas may inspect inventory; only the receipt recovery/retirement owner may request lifecycle mutations. Physical cleanup must go through this owner and the producer barrier, with no independent age-based cleanup thread in multi-executor mode.

Convergence takes the deduplicated union of occupied receipts and executable/terminating queue Jobs; an independently verified server-retired inert tombstone is excluded. Unrecognized or merely labeled tombstones count as uncertainty. Never use a filtered inventory count alone. An unmatched Job causes pool quarantine/import under an operator-reviewed migration. Unknown inventory blocks new claims. An extra replica must not multiply reported capacity; Console totals use one pool policy/version and verified global occupancy, while instance health stays separately observable.

## Recovery budgets and evidence

These are proposed acceptance deadlines, conditional on healthy Work/Kubernetes APIs and an eligible node. They are not current SLO claims:

| Boundary                                                                                                                | Proposed bound                                                             | Failure behavior                                             |
| ----------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- | ------------------------------------------------------------ |
| Idle healthy executor claims a queued, allowed run with a free slot                                                     | Existing 15-second poll; p95 under 2 minutes                               | Capacity/cooldown/placement exclusions measured separately   |
| Another replica continues after a confirmed controller process crash, with a free slot/domain and placement eligibility | First safe claim within 60 seconds                                         | Existing receipts remain occupied and workers continue       |
| Original never-started owned Job handoff recovery                                                                       | Start next bounded sweep within 15 seconds; current 20-second sweep budget | Same UID/token; no duplicate attempt                         |
| Both replicas' cron service after one crash                                                                             | Next successful tick within 5 minutes plus bounded request time            | No dependence on cluster launch readiness                    |
| Unknown producer or node partition                                                                                      | Alert after 2 minutes; no automatic slot-release deadline                  | Explicit quarantine until positive fencing/physical evidence |
| Receipt convergence once fencing and physical termination are proven                                                    | Two bounded reconciliation sweeps, at most 60 seconds                      | CAS mismatch re-reads; no unconditional decrement            |

Expose bounded labels for pool readiness/state, occupied slots (`unplaced`, `placed`, `retiring`, `quarantined`), free slots, receipt transitions/refusals, fence failures, oldest quarantine age, recovery latency, policy mismatch, and last successful inventory. Preserve existing claim/launch/provider and maintenance metrics. Do not put run IDs, tokens, arbitrary error text or producer IDs in metric labels; logs and bounded authenticated evidence carry exact receipt/UID identities. Alert on conservation violations, stale inventory, unresolved retirement, absent healthy executors and stale cron success. Missing samples cannot imply zero occupancy or healthy capacity.

## Failure-injection acceptance

Implement the mechanisms before running these tests; a model of the proposal is not proof of deployed HA:

| Injection                                                                                                     | Required observation                                                                                                 |
| ------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| Two real store claim transactions, `N=1`, same/different provider grants                                      | One occupied receipt/claim only; ceilings and fairness remain server-owned                                           |
| Kill before claim response, after response, after Job create, after Secret create, and before/after unsuspend | Receipt never disappears; recover same run/UID when safe; otherwise quarantine                                       |
| Stop or partition one producer after authorization, then resume it after successor recovery                   | Delayed launch/delete/release cannot free capacity or mutate a newer UID; uncertain writes retain the tombstone/slot |
| Logical lease expires or report completes while its Pod remains running/terminating                           | No slot/provider capacity freed; retry waits physically                                                              |
| Job create times out after persistence; object replaced under the same name                                   | Read same identity; refuse replacement UID, no duplicate recreation                                                  |
| Work/Kubernetes API failure, partial inventory, absent Secret, missing receipt                                | Fail closed, bounded calls, actionable evidence, no secrets in logs                                                  |
| Concurrent schedule/maintenance/recovery ticks                                                                | One scheduled item/run per due slot; bounded retries/outbox effects and receipt fencing                              |
| Policy limit reduction or old/new executor configuration overlap                                              | Reject mismatched versions; drain without crossing either active bound                                               |
| Cleanup/TTL and former producer race                                                                          | No tombstone deletion before quiescence; exact UID retirement; never force-delete to claim termination               |
| Return the former controller and replay its old acknowledgements                                              | Stale nonce/incarnation cannot release a successor's slot or re-create a retired run                                 |

Run store races against MemoryStore and the Firestore emulator, actual Go clients against a controlled Kubernetes API, and the split-brain/termination cases on an approved disposable staging cluster. Then use a genuine authorized issue/work item for failover proof with retained runtime observations. A green unit test or leader-election demo does not establish the physical fence.

## Migration, rollout, and rollback

1. Land the receipt schemas/transactions/API behind a disabled deployment setting, then land receipt-aware executor/recovery/cleanup, cron concurrency checks and observability. Preserve old singleton behavior while disabled; the new server refuses legacy claims once a pool is enforced.
2. Homelab prepares reviewed pool/identity configuration, the separate positive-fencing authority, controlled staging failure scripts and metric/alert changes. No running replica, credential, Kubernetes, IAM, Terraform or flag changes occur in this design task.
3. With explicit operation approval, stop/drain **and positively fence** the singleton producer; inventory its exact Jobs, Pods, claimed pre-Job runs and potential unfinished RPCs. Import occupied receipts through an application-owned migration with reviewable dry-run evidence. Unknown state quarantines the pool; do not seed zero occupancy. Enable enforcement before any multi-executor claim.
4. Run one receipt-aware executor first, then a second on a separate declared host/failure domain, with the same pool/version. Verify shared occupancy, provider limits, cron and all failure injections; retain canary observations before declaring R8 shipped. Physical resource sizing and ARC placement remain Homelab decisions.
5. Roll back to **one receipt-aware** executor while leaving server enforcement and receipts intact. Fence removed producer incarnations and reconcile occupied attempts. Reverting to legacy local accounting requires an explicitly reviewed drain/fence/empty-pool migration; never disable the fence while any receipt or worker may be active.
